# Uers Permissions

- Defines what action can a user, group can perform in the system.

- Actions modes: ``read`` a file or folder, ``write`` into a file, ``execute`` a script.


## What does `ls -l` gives:

- Long listing of files and folders in current directory.

```bash
<permission> <no_of_hard_link>  <user_owner>  <group_owner> <file_size_in_bytes> <last_modified_date> <last_modified_time> <file_name>
```

```bash
ls -l
drwxrwxr-x 2 test surya 4096 Dec 10 12:33 folder
```

- ``drwxrwxr-x`` => Permission
- ``2`` => Hard Link Number
- ``test`` => Usser owner of file
- ``surya`` => Group owner of file
- ``4099`` => File size in bytes.



## Permissions Representation:

- **Owner Permission:** Defines what a owner can do with.

- **Group Permission:** Defines actions permitted by the group owner of file.

- **Other Users:** Defines actions that can be performed by other than own and a group.

> **Note:** Group owner permission also relates to the actions that can be performed by the user  in the owner group.

**Representation:**

- **1st field:** Defines a file type.
     - `-`: Regular file
     - `d`: Directory
     - `l`: [Symbolic link](https://www.freecodecamp.org/news/symlink-tutorial-in-linux-how-to-create-and-remove-a-symbolic-link/), similar to how shortcuts are created in windows.
     - `c`: character device file.
     - `b`: block device file
     - `s`: socket file
     - `p`: Named Pipe (FIFO)
    
- **9 fields representing:**
    - **First 3 field:** For owner
    - **Second 3 field:** For Group
    - **Last 3 field:** For other than group and owner




```bash
ls -l
# drwxrwxr-x 2 test test 4096 Dec 10 12:33 folder
```

- 


Interpretation: ``d rwx rwx r-x``
- `d` represents its'a directory.
- `rwx` represents a user owner can read, write and execute.
- `rwx`represents a group owner can read, write and execute.
- `r-x` represents other user can read and execute but cannot write.

## Changing Permission:

```bash
chmod [options] [permission] [file]
```


**Options include:**
- `-c` gives the message of change after permission change is made.
- `-R` for recursively changing the permissions of the files and folders inside directory.

**Permission Add / Remove with Symbolic Representation:**

Basic Syntax: ``chmod [options] <u/g/o><+/-><permission> <file>``

- `u` to change permission for user owner of a file.
- `h` to change the permission for group owner of file.
- `o` to change the permission for other users.
- `+` to add a permission.
- `-` to remove a permission.

- ``chmod u+rwx,g+r,o+r <file>`` => This gives user owner, read write and execute permission, group owner and other user read only permission,

- ``chmod u-x,g-wx,o-rwx <file>`` => This removes the execute permission for user owner, write and execute permissions for group owner, read write and execute permission for other users.

**Permission Add / Remove With NUmeric Representation**

``chmod <user_permission><group_permission><other_permission>``

```sh
4   2   1
r   w   x
```

Binary representation of ``111`` => 7 means read, write and execute.

Permission Digit Can be:
- ``0`` => for no any permission
- ``1`` => Execute permission
- ``2`` => Write Permission
- ``4`` => Read Permission
- `5` => 4 (read) + 1 (execute)
- `7` => 4 (read) + 2 (write) + 1 (execute)

Basically, combinations of permissions are created by summing, `r=4, w=2. x=1`. While `0` representing no permission.

## Example:

**With: Symbolic Representation**

```bash
#  create a file
touch file.txt

# view perm: User Owner=> rw- Group Owner=> rw- Other=> r--
ls -l
-rw-rw-r-- 1 test test 0 Dec 13 10:28 file.txt

# remove read permission for other, and add execute perm for user and group owner
chmod -c u+x,g+x,o-r file.txt
# mode of 'file.txt' changed from 0664 (rw-rw-r--) to 0770 (rwxrwx---)

# recursive usage
mkdir folder
touch folder/file1.txt
touch folder/file2.txt

# view permissions inside folder directory: User owner => -rw- , Group Owner=>  rw- , Other=> r--
ls -l folder
# -rw-rw-r-- 1 test test 0 Dec 13 10:38 file1.txt
# -rw-rw-r-- 1 test test 0 Dec 13 10:38 file2.txt
```

**With Numeric Representation:**

```bash
# recursive usage
mkdir folder
touch folder/file1.txt
touch folder/file2.txt

# change permission recursively: rwx (111 / 7) for user owner only.
chmod -R 700 folder/

# check changes
ls -l folder/
# -rwx------ 1 test test 0 Dec 13 10:38 file1.txt
# -rwx------ 1 test test 0 Dec 13 10:38 file2.txt
```

**Note: Use ``-c`` flag option to view changes.**

**If changing a group owner permission, the permission for a file or folder is impacted for other user in group.**


## Setuid, Setguid, Stickt Bit

- Allows to rwx file or folder as a user (setuid) or a group owner (setgid) of the file/folder

- ```chmod g<+/->s``` to add(+)/remove(-) a groupbit.

- ```chmod u<+/->s``` to add(+)/remove(-) a userbit.

- ```chmod <+/->t``` to add(+)/remove(-) a stickybit.

## Representation in permission bits

- Setuid is represented with ``S/s`` in 4th bit. (Last Bit of User perm bits.)

- Setgid is represented with ``S/s`` in 7th bit. (Last bit of group perm bit)

- Stickybit is represented with ``T/t`` in 10th bit.(Last bit of other perm bit.)

```bash
# ----------------------------------------------------------------------
# create a test file
touch test_file

# view perm:
ls -l
# -rw-rw-r-- 1 test test 0 Dec 14 19:02 test_file
# ----------------------------------------------------------------------

# ----------------------------------------------------------------------
# add a setuid bit
chmod u+s test_file

# view perm: 
ls -l
# -rwSrw-r-- 1 test test 0 Dec 14 19:02 test_file
# ----------------------------------------------------------------------

# ----------------------------------------------------------------------
# add a setgid bit
chmod g+s test_file

# view perm: 
ls -l
# -rwSrwSr-- 1 test test 0 Dec 14 19:02 test_file
# ----------------------------------------------------------------------

# ----------------------------------------------------------------------
# add a sticky bit
chmod +t test_file

# view perm: 
ls -l
# -rwSrwSr-T 1 test test 0 Dec 14 19:02 test_file
# ----------------------------------------------------------------------
```

Here, capital letter represents that there is no execute permission for the user owner, group owner or other users.

Let's add a execute permissions for user, group and other, it should change to small letters.

```bash
# ----------------------------------------------------------------------
# add a setuid bit
chmod u+x test_file

# view perm: 
ls -l
# -rwsrwSr-T 1 test test 0 Dec 14 19:02 test_file
# ----------------------------------------------------------------------

# ----------------------------------------------------------------------
# add a setgid bit
chmod g+x test_file

# view perm: 
ls -l
# -rwsrwsr-T 1 test test 0 Dec 14 19:02 test_file
# ----------------------------------------------------------------------

# ----------------------------------------------------------------------
# add a sticky bit
chmod o+x test_file

# view perm: 
ls -l
# -rwsrwsr-t 1 test test 0 Dec 14 19:02 test_file
# ----------------------------------------------------------------------
```

Thus, with a execute perm for specific user, group or other, letter turns to small. Otherwise it's represented with capital letter.

### Setuid

When a file with setuid is executed, the process runs with the privileges of the file's owner, regardless of who executes it, 
provided that user have permission to execute a file.


We've a above code in file named: ``code.c``
```c
#include <stdio.h>
#include <unistd.h>


int main(int argc,  char **argv) {
    // initialize a file pointer
    FILE *fp;

    // open a file in append mode:
    fp = fopen("file.txt", "a");

    // add a character into file with file pointer
    fputc('a', fp);
    fputc('b', fp);
    fputc('\n', fp);
    
    // current effective user id
    printf("Executing UserID: %d\n", geteuid());

    // close file
    fclose(fp);
    return 0;
}

```

Note that there's a difference in ``logname``, ``id``, ``euid``

**Compile and make script executable**

```bash
# compile code.c into binary executable
gcc -o binary code.c

# list
ls -l => Note, user, group and other user have a execute permission
# -rwxrwxr-x 1 test test 16176 Dec 14 20:08 binary

```

**Execute as a owner of a file**
```bash
# check current user: User id is => 1003
id -u
# 1003

# try executing as a same user: id => 1003
./binary
# Executing UserID: 1003

# check the content of file, file.txt
cat file.txt
# ab
```

**Execute as a different user:**

```bash
# check current user: User id is => 1000
id -u
# 1000

# execute binary
./binary
# Segmentation fault (core dumped)
```

So without a setuid bit set, user other than the owner of a binary cannot execute a file.

**Add a setuid bit and execute**

```bash
# check current user: User id is => 1000
id -u
# 1000

# let's add a setuid bit.
sudo chmod u+s binary

# execute a binary now => Note the UserID executing a script is different.
./binary 
# Executing UserID: 1003

# check content of file:
cat file.txt
# ab 
# ab
```

Thus, with a setuid bit set, it allows us to run a binaries, or some codes as a owner of that file/script.


### Setgid:

- Used to rwx as a group owner of a file.

- ```chmod g<+/->s``` to add(+)/remove(-) a setgid bit.




```bash
# login as a test user
su test

# create a directory
mkdir folder

# view permissions: User Owner => rwx Group Owner=> rwx Other=> r-x
ls -l
# drwxrwxr-x 2 test test 4096 Dec 13 11:37 folder

# lets add rwx permission for other users too
chmod o+rwx folder

# check the permission: Added rwx permission for other user too.
ls -l
# drwxrwxrwx 2 test test 4096 Dec 13 11:37 folder

# now change the group bit for directory
chmod g+s folder

# view changes: User owner => rwx Group Owner => rws Other => rwx
ls -l
# drwxrwsrwx 2 test test 4096 Dec 13 11:45 folder
```

Not let's login as a other user:

```bash
# login as a surya user
su surya

# check if user is in test group: => No output means, no
id -Gn $USER | grep test

# lets try to create a file and directory inside the test user folder
touch /home/test/folder/file.txt
mkdir /home/test/folder/subfolder

# let's see the group owner of a file: Notice the user owner is surya, but a group owner is test.
ls -l /home/test/folder/
# -rw-rw-r-- 1 surya test    0 Dec 13 11:50 file.txt
# drwxrwsr-x 2 surya test 4096 Dec 13 11:50 subfolder
```

**Thus, if a groupbit is set for a directory, a file or folder inside the directory will have a group owner of a parent directory.**

## Sticky Bit

This permission does not affect individual files.However, at the directory level, it restricts file deletion and renaming.  Only the owner (and root) of a
file can remove the file within that directory.

- ```chmod <+/->t <file_name>``` to add(+)/remove(-) a stickybit.


When the **sticky bit is set on a directory:**
Files in the directory can be deleted or renamed only by:
- The owner of the file.
- The owner of the directory.
- A privileged user (e.g., root).

When the sticky bit is set on a directory, users in a group cannot delete or rename files in that directory unless they own the files. 
This restriction applies even if the group has write permissions for the directory.

> As a user test:

```bash
# create a folder
mkdir folder

# check a permission:
ls -l
# drwxrwxr-x 2 test test 4096 Dec 19 11:31 folder

# set a sticky bit for directory:
chmod +t folder

# view perm changes:
drwxrwxr-t 2 test test 4096 Dec 19 11:31 folder

# lets create a file and a folder inside the folder dir
mkdir folder/folder
mkdir folder/file

# check perms
ls -l folder/
# -rw-rw-r-- 1 test test    0 Dec 19 11:43 file
# drwxrwxr-x 2 test test 4096 Dec 19 11:43 folder
```

> As a user surya

```bash
# try deleting
rm -rf folder/
rm: cannot remove 'folder/': Operation not permitted

# rename
mv folder folder2
# mv: cannot move 'folder' to 'folder2': Operation not permitted

# try creating a file and folder with current user:
touch suryas_file
mkdir suryas_directory

# remove all with surya* => Removes
rm -rf surya*
```

So, with sticky bits (set for directory), only a owner, superuser, can delete or rename a file inside a directory.




## Numeric Representation With Setuid, SetGid, Sticky Bits:

Normally if we dont want to touch those bits, we have 3 numbers: ``<user_perm><group_perm><other_perm>``

But with bits we can add extra bit at first: ``<bit><user_perm><group_perm><other_perm>``

- If `<bit>` value is ``1`` => Sticky bit is set.
- If `<bit>` value is ``2`` => setgid bit is set.
- If `<bit>` value is ``4`` => setuid bit is set.
